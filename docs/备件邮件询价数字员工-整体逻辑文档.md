# 备件邮件询价数字员工 —— 整体逻辑文档

> 版本：V1.2 ｜ 代码位置：`app/routes_procurement_agent.py`、`app/mcp_tools.py`、`app/db/spare_mail.py` ｜ Skill 定义：`skills/skill-proc-mail-inquiry.json`

---

## 1. 定位与设计原则

本数字员工与现有「备件采购员工」**平行独立**，不改动原有代码。实现从**工程师发起询价 → 供应商报价 → 审批人确认 → 下达订货 → 供应商发货回执 → 工程师确认完成 → 结算邮件**的全流程邮件自动化。

三条核心设计原则：

| 原则 | 说明 |
|------|------|
| **邮箱权威** | 邮件流（`In-Reply-To` / `References`）是会话链的真正来源；邮件**原文不落库**，仅在首次解析时读一次，把结果落库，后续步骤直接用库中结构化字段。G 结算邮件的 References 链按「邮箱权威」在发送时实时从 Sent 目录 fetch |
| **静态配置入库** | 邮件凭据、审批人、供应商池、模板统一存 DB `spare_mail_config`，Skill JSON 仅作底稿/兜底，热加载后 DB 优先覆盖 |
| **单表动态状态** | 运行态任务只落 `spare_mail_task` 一张表，字段覆盖内/外双流全部关键信息 |

## 3. 双邮件流模型（核心）

系统区分两条互相独立、异步推进的邮件流：

![双流全景](images/双流.png)

| 流 | 线程 | 参与者 | 阶段 |
|----|------|--------|------|
| **内部流** | 工程师询价线程（A 邮件为根，`thread_msg_id`） | 工程师↔智能体↔审批人 | `R_INIT → R_APPROVAL → R_CLOSED` |
| **外部流** | 供应商询价线程（B 邮件为根） | 智能体↔供应商 | `R_SEND → R_WAIT_QUOTES → R_DECIDING → R_ORDER → R_WAIT_SHIPPING` |

**关键约束：同一流内的邮件必须持续在同一线程上回复**（通过 `In-Reply-To` + `References` 维持），即使跨分支也不能新建邮件。两条流各自在对应线程上推进，互不抢占。

## 4. 状态机

### 4.1 内部流（`internal_status`）

| 状态 | 动作 | 迁移条件 |
|------|------|----------|
| `R_INIT` | `_mi_internal_send_d`：报价就绪后发模板 D 汇总（回复工程师线程 + 抄送审批人） | `lowest_supplier` 非空（外部流已定最低价） |
| `R_APPROVAL` | `_mi_internal_wait_approval`：按发件人区分两分支 | — |
| ├─ 审批人回复确认 | 设 `target_supplier`、`approval_state=approved`、记 `approver_email` | 回复在 D 线程，命中「确认采购/同意采购/批准采购…」 |
| ├─ 审批人回复全部拒绝 | 发模板 F 中止 → 双流终态 `R_ABORT/DONE` | 命中「全部报价不可选/任务终止…」 |
| ├─ 工程师回复「备件更换完成」 | 向选中供应商线程发模板 G 结算 → 双流终态 `R_CLOSED/DONE` | 非审批人，命中「备件更换完成/更换完成…」 |
| `R_CLOSED` | 终态 | — |

### 4.2 外部流（`external_status`）

| 状态 | 动作 | 迁移条件 |
|------|------|----------|
| `R_SEND` | `_step_sending_b`：发模板 B 询价给供应商池（不含收货地址） | 创建任务后 |
| `R_WAIT_QUOTES` | `_step_waiting_quotes`：抓报价，解析报价/数量/成色/发货时间入库 | 全部供应商已回 **或** 报价截止时间到 |
| `R_DECIDING` | `_step_deciding_lowest`：算最低价 + 未选中供应商标记截止；无有效报价 → 模板 F 中止 | 报价集合完备 |
| `R_ORDER` | `_step_ordering`：**等待内部审批确认 `target_supplier`**，批复后在选中供应商报价线程发模板 E 订货（含收货地址） | `target_supplier` 非空 |
| `R_WAIT_SHIPPING` | `_mi_step_wait_shipping`：等选中供应商回快递单号，存 `shipped_no` → `R_CLOSED` | 收到单号 |

**协作点**：内部流 `R_APPROVAL` 分支「审批确认」写入 `target_supplier`，外部流 `R_ORDER` 检测到后再发 E。两流在 tick 的两次 pass 中接力完成。

> Legacy 别名（兼容旧 dashboard）：`R_SEND→SENDING_B`、`R_WAIT_QUOTES→WAITING_QUOTES`、`R_DECIDING→DECIDING_LOWEST`、`R_APPROVAL→WAITING_APPROVAL`、`R_ORDER→ORDERING`、`R_WAIT_SHIPPING→SHIPPING`。

## 5. 完整时序（A→G）

```
[A] 工程师(张运维/b1) 发起询价邮件（无任务号）
        │  线程根：thread_msg_id
        ▼
[解析] 智能体(采购智能体/b4，本体轨) 读该邮件 → 正则/LLM 抽取字段() → 落 O_Task，生成任务号 OT-<md5>
        │  外部流 R_SEND
        ▼
[B] 智能体 向供应商池各发询价函（中软国际/b2、神州数码/b6 等比价，主题带 [任务号]，不含收货地址）
        │  外部流 → R_WAIT_QUOTES
        ▼  供应商在B线程回复（In-Reply-To=B）
[C] 供应商(中软国际/b2、神州数码/b6) 报价邮件 → 解析报价内容入库（quotes）
        │  全部回复或截止 → 外部流 R_DECIDING（智能体固定选最低价）
        │  内部流 R_INIT → R_APPROVAL
        ▼
[D] 智能体 发 D 汇总审批邮件（回复工程师线程 + 抄送审批人 李审批/b5）
        ▼  审批人在D线程回复
[审批] 李审批(b5) 确认 → target_supplier=最低价供应商、approval_state=approved
        │  外部流 R_ORDER（检测到 target 后）
        ▼  在选中供应商报价线程回复
[E] 智能体 下订单 E（含收货地址/联系人，主题带 [任务号]）
        │  外部流 → R_WAIT_SHIPPING
        ▼  供应商在E线程回复快递单号
[F] 供应商 回单号 → tracking_no 入库 → 外部流 R_WAIT_SHIPPING→R_CLOSED
        ▼  工程师在A线程回复"备件更换完成"
[确认] 张运维(b1) 确认完成（非审批人分支）
        │  内部流 → R_CLOSED，发结算
        ▼  在选中供应商E线程回复（References 实时 fetch 拼全链）
[G] 智能体 向选中供应商发结算/流程关闭邮件 → 任务 DONE
```

任务在 tick 的每次 pass 内按 `R_SEND` 等各状态从 DB 列表扫出活动任务，逐状态推进。单任务异常被 try/except 隔离，不阻塞其它任务。

## 7. 数据流与"邮箱权威"落实

```
邮件流(真相源)                  DB(结构化快照)                   下游消费
─────────────────            ─────────────────            ─────────────────
A 工程师询价 ──首次解析──> project_no/brand/pn/…/  ──> B询价渲染
                              threat_msg_id
B 询价 ──发信时──> suppliers_json[].msg_id      ──> C报价线程匹配
C 报价 ──首次解析──> quotes_json[]/lowest_*      ──> D汇总渲染
D 审批 ──发信时──> d_mail_msg_id                ──> 审批线程匹配
审批 ──首次识别──> target_supplier/approver_*/  ──> E订货
F 回单 ──首次解析──> shipped_no                  ──> 结束
G 结算 ──发送时──> (References)←Sent实时fetch    ──> 全链完整
```

关键点：
1. **邮件原文不反复解析**——每封关键邮件只在其状态首次处理时读一次并落库，后续步骤直接用库字段，避免每次 tick 重扫正文。
2. **线程锚点靠 Message-ID**——每条回复用 `In-Reply-To`/`References` 承接上游，识别上游也靠 `match_in_reply_to_msg_ids` 精确匹配，而非全文搜索。
3. **G 结算例外**——References 全链在发送时由 `_fetch_sent_mail_refs` 从 b3 Sent 目录实时读取（邮箱权威），因为链若拼错整个线程就断了，实时取最稳。
4. **UNSEEN 增量**——tick 开头 `_tick_prefetch_unseen` 一次拉取全部 UNSEEN 存缓存，后续 step 复用；若 UNSEEN 返回 0 封则清缓存回退全量 `SINCE` 拉取（应对 163 IMAP UNSEEN 不稳定）。

## 8. 线程与调度

- **无独立常驻线程/进程**。流程由 `scheduler/tick?kind=mail-inquiry` 驱动，定时轮询（scheduler 主流程调用，轮询间隔按其配置，长周期任务）。
- 每条 tick 的 pass：
  1. `_tick_prefetch_unseen(cfg)`：拉一次 UNSEEN 缓存。
  2. `_step_parsing(cfg, tpls)`：抓取"工程师发起询价"新邮件 → 解析 → 建任务（含校验缺失字段）。
  3. `spare_mail_list_tasks(page_size=2000)`：拉活动任务。
  4. **内部流 pass**：遍历 `internal_status in {R_INIT,R_APPROVAL}`，调 `_mi_step_internal`。
  5. **外部流 pass**：遍历 `external_status in {R_SEND,R_WAIT_QUOTES,R_DECIDING,R_ORDER,R_WAIT_SHIPPING}`，调 `_mi_step_external`。
  6. 每任务独立 try/except，异常记 `latest_step=*_ERROR:*`，不阻塞其它任务；`_TICK_MAX_TASKS` 限制单 pass 处理量。
- 长周期轮询邮箱是常态；询价时效（报价截止）在报价处理分支判断 `now >= inquiry_deadline` 触发。

## 9. 邮件模板（Skill `templates`）

### A-工程师发起询价
- 主题：`【备件询价】{project_no} {project_name} — {brand} {pn} x {count}`
- 正文：项目/备件类型/品牌/PN/规格/成色/数量/紧急程度/最晚发货时间，含任务号 `{task_no}`。
- **唯一例外**：工程师初始邮件由**人**发送，不带任务号（任务号是系统后续生成的）。

### B-对外询价（不含收货地址）
- 主题：`【询价】{project_no} {brand} {pn} x {count} — {urgent} 内回复 [{task_no}]`
- 正文：向供应商询价，含规格/成色/数量/最晚发货/**询价截止 {deadline}**，注明收货信息待订货阶段告知，**主题带任务号**。

### C-供应商回复（系统自动归档，非系统发送）
- 仅作展示模板；实际由供应商邮件触发，系统解析报价内容入库。

### D-内部汇总-最低价优选-抄送审批人
- 主题：`【询价汇总】{project_no} {brand} {pn} — {suppliers_count}家报价-最低价优选 [{task_no}]`
- 正文：报价列表 `{suppliers}`、系统最低价提示 `{lowest_quote}`/`{lowest_supplier}`，请审批人 `{approver_emails}` 确认；回复工程师线程 + 抄送审批人，**主题带任务号**。

### E-下达订货（回复选中供应商报价线程，带收货地址）
- 主题：`【订货确认】{project_no} {brand} {pn} x {count} — 请安排发货 [{task_no}]`
- 正文：订货明细 + 收货信息（收货人/电话/地址）+ 交付要求（最晚发货、快递单号 2h 内回复）+ 随货测试报告/成色证明；在选中供应商 C 报价线程回复，**主题带任务号**。

### F-中止通知
- 主题：`【询价中止通知】{project_no} {brand} {pn} — 任务已终止 [{task_no}]`
- 正文：中止原因 `{stop_reason}`；用于审批全部拒绝或无有效报价场景。

### G-采购结束结算（外部流完成后发供应商）
- 主题：`【采购结束】{project_no} {brand} {pn} — 任务关闭 [{task_no}]`
- 正文：确认收货并完成更换，进入结算；订货摘要（备件/成色/数量）；在选中供应商 E 线程回复，**References 实时拼全链**（B→C→E）。

模板统一占位符：`{project_no} {project_name} {part_type} {brand} {pn} {spec} {condition} {count} {address} {urgent} {latest_ship_time} {deadline} {deadline} {suppliers_count} {suppliers} {lowest_quote} {lowest_supplier} {approver_emails} {supplier} {quote} {receiver_name} {receiver_phone} {condition_display} {stop_reason} {task_no}`；渲染用 `_safe_format`（缺失占位符不抛错）。

## 10. 配置来源优先级

```
DB spare_mail_config (proc_credentials / proc_participants / proc_templates)
        ↑ 优先覆盖
Skill JSON (skills/skill-proc-mail-inquiry.json config/templates)
        ↑ 兜底
```

- 单条参与方 upsert：`INSERT ... ON CONFLICT(config_key) DO UPDATE` 整体覆盖该 key。

## 11. 异常与终止场景

| 场景 | 处理 |
|------|------|
| 工程师初始邮件缺关键字段（如规格） | 解析时校验，缺失则记录，不推进建任务（或按需回邮件指出问题，属待补分支） |
| 没有发送成功的 B 询价 | `R_WAIT_QUOTES` 直接转 `R_DECIDING`，走无有效报价分支 |
| 无有效报价 / 全部迟到 | `_step_deciding_lowest` 发模板 F 中止 → 双流终态 |
| 审批人全部拒绝 | `_mi_internal_wait_approval` 发模板 F → `R_ABORT/DONE` |
| 供应商从非白名单地址报价 | 报价在供应商列表匹配失败 → 忽略 |
| 报价迟到 | 标记 `is_late=true`，不参与最低价优选 |
| 报价截止用 `urgent` 时间（`5min/1h/24h…`）换算 `inquiry_deadline` 落库 | 报价处理时 `now >= deadline` 判定到点即决策 |
| 单任务异常 | 记 `latest_step`，try/except 隔离，同一 tick 继续其它任务 |
| 163 IMAP 限流/UNSEEN 空 | 回退全量 `SINCE` 拉取 |
